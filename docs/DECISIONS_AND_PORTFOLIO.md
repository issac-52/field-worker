# Field Work Manager — 기술 의사결정 및 포트폴리오 로그

> 업데이트: 2026-10-19  |  상태: 개발 초기  |  납기: 2026-11-14
>
> 목적: 면접 및 포트폴리오를 위해 **결정 근거·대안·트레이드오프·실제 해결 과정·검증 결과**를 지속적으로 기록한다.
>
> 표기: **결정**(방향 확정) / **완료**(사용자 확인 또는 실제 실행) / **계획**(미구현) / **보류**(요구사항 대기) / **검증 필요**(확인 전). 구현한 것으로 부풀려 쓰지 않는다.

## 1. 프로젝트 개요

- 배경: 약 20명의 현장 아르바이트 작업자와 관리자가 사용하는 모바일 중심 현장 조사/업무 관리 웹 서비스.
- 업무 흐름: 관리자 엑셀 업로드(약 2,000행, 주소 포함) → 정제·검증 → 주소의 좌표 변환 및 저장 → 지도 마커 표시 → 작업자가 기존 기초 데이터에 현장 상세정보와 사진 4장 추가 → 임시저장/완료 → 변경 이력 및 건당/월별 정산 → 전체/조건별 엑셀 및 지정 한글 문서 형식으로 출력.
- 모바일 우선. PC는 관리자 통계, 보정 및 내보내기 중심.
- 개발비 약 100만 원; 서버는 2027년 초~중반 종료 예정. 운영비를 무료 크레딧·무료 플랜 내에서 최소화.
- 고객 원본 엑셀, 상세 폼, 한글 문서 템플릿은 아직 미수령. 실제 필드와 문서 출력 범위는 미확정.
- 개인정보·업무 데이터의 외부 공개 및 포트폴리오 재사용은 고객 승인 후 진행.

## 2. 현재 사실과 환경 구분

| 영역 | 상태 | 확인 내용 |
|---|---|---|
| EC2 | **완료** | AWS 서울 리전 Ubuntu 서버 생성, SSH 접속 성공. t3.small/디스크 크기 실제 콘솔 재확인 필요 |
| SSH 키 권한 | **완료** | Windows PEM 접근 권한 과다 오류를 `icacls`로 제한한 후 SSH 접속 성공 |
| Docker | **완료** | Docker Engine 및 Compose 설치, `hello-world` 동작 확인(사용자 보고) |
| PostgreSQL | **완료** | Docker Compose 기동, `pg_isready` 및 `psql SELECT version()` 성공(사용자 보고) |
| Spring Boot API | **계획** | 서버/로컬 연결 및 인증 아직 미구현 |
| FE | **계획** | React/Vite 정식 기능·Cloudflare Pages 배포 미완료 |
| R2 | **보유** | 기존 Cloudflare R2 사용 중; 이번 서비스의 권한/버킷 연동은 미구현 |
| Maps 및 Geocoding | **계획** | NAVER Maps API 연동 미완료 |

**주의:** 이전에 생성한 스타터 ZIP은 Maven, Spring Boot 설정과 `docs/decisions.md` 및 개발용 DB 구성의 **초안**이다. 본 문서의 의사결정은 스타터 파일에 자동 반영된 게 아니며, 실제 구현 시 Java/Spring Boot 버전, DB 버전(서버에서 설치한 PostgreSQL 17 vs 스타터의 16), 인증 및 배포 설정을 하나로 정리해야 한다.

## 3. ADR — 기술 의사결정 기록

### ADR-001: 네이티브 앱 대신 React + Vite 모바일 웹
- **상태:** 결정
- **맥락:** 약 20명이 개인 휴대전화로 현장 기록, PC는 관리자 중심. 짧은 납기.
- **선택:** React, TypeScript, Vite; 모바일 우선 반응형 SPA.
- **대안:** React Native/Flutter, Next.js SSR.
- **근거:** 별도 앱 설치·스토어 심사 불필요, SSR/SEO 필요 낮음, 기존 React 역량 재사용, 빠른 구현과 배포.
- **트레이드오프:** 오프라인 작업과 백그라운드 업로드는 별도 설계 필요. 모바일 사진 권한/브라우저 동작 실기기 테스트 필요.
- **검증:** 현장 휴대폰에서 사진 촬영/파일 선택·지도 성능 테스트.

### ADR-002: Java 21 + Spring Boot 모듈러 모놀리스
- **상태:** 결정(빌드 도구/버전 정합성 재확인)
- **맥락:** 인증, 엑셀 변환, 기록 이력, 정산과 문서 생성이 한 시스템에 들어감. 단기 외주, 20명 규모.
- **선택:** Spring Boot 단일 애플리케이션, 도메인별 패키지; Java 21.
- **대안:** Next.js BFF/Supabase 전용, 여러 마이크로서비스.
- **근거:** Spring/Java 경험 활용, 권한·트랜잭션·감사 로그·파일 처리의 명시적 설계, 서비스 규모에 적합.
- **트레이드오프:** 서버 운영 부담 존재; MSA 대비 독립 확장은 제한되나 현재 불필요.
- **검증:** Spring Boot ↔ PostgreSQL 연결, 인증 통합 테스트, 동시 완료 테스트.

### ADR-003: PostgreSQL + Flyway, 초기 단일 EC2 호스팅
- **상태:** 결정 / PostgreSQL 인프라 완료
- **맥락:** 주소/좌표, 사용자, 작업 기록, 정산의 참조 무결성 필요. 운영비 최소화.
- **선택:** PostgreSQL, 마이그레이션은 Flyway, EC2에서 Docker Compose로 실행.
- **대안:** RDS(관리 편하지만 고정비), MongoDB, 별도 DB VM.
- **근거:** 관계형 무결성과 트랜잭션, 필요 시 JSONB로 가변 입력값 수용, 초기 월 비용 절감.
- **트레이드오프:** 앱과 DB가 단일 장애 지점을 공유하며 OS 패치, 백업 및 복구 책임이 개발자에게 있음.
- **검증:** EBS 영속성, 외부 5432 비공개, 자동 백업과 복원 리허설.

### ADR-004: AWS EC2 프리 플랜 크레딧 활용
- **상태:** 결정 / EC2 및 SSH 완료
- **맥락:** AWS Free 플랜, 약 $100 크레딧과 약 100일 잔여로 보고, 2027년 초~중반 서비스 종료 예정.
- **선택:** EC2 하나에 API/DB 구성, 개발하지 않을 때 Stop, 운영 시작 후 24시간 실행.
- **대안:** Oracle Always Free, Railway, AWS Lightsail.
- **근거:** 보유 크레딧 활용, 운영 기간이 짧고 AWS 배포·Linux·보안그룹·Docker 경험을 쌓을 수 있음.
- **트레이드오프:** 무료 기간/크레딧 종료 전에 Paid 전환 또는 철수 필요. EBS와 공인 IPv4는 정지 중에도 별도 요금 가능.
- **검증:** AWS 콘솔에서 Free 플랜 만료일, 크레딧 유효기간·잔여액, 예산 경보와 월 예상 비용 점검.

### ADR-005: Cloudflare Pages 프론트엔드 호스팅
- **상태:** 결정(배포 미완료)
- **맥락:** 브라우저에서 접근 가능한 HTTPS 프론트 URL이 필요, 운영비 최소화.
- **선택:** Cloudflare Pages의 `*.pages.dev` 기본 주소 + Vite 정적 빌드.
- **대안:** Vercel, EC2에서 프론트도 서빙.
- **근거:** 별도 도메인 구매·프론트 서버 관리 불필요, 무료 정적 배포, 기존 Cloudflare 생태계 사용.
- **트레이드오프:** API는 별도 HTTPS 주소가 필요하고 쿠키/CORS 정책을 맞춰야 함.
- **검증:** Pages에서 모바일 HTTPS 접속, SPA 라우팅 새로고침, API 호출 확인.

### ADR-006: Cloudflare R2에 현장 사진 저장
- **상태:** 결정(연동 미구현)
- **맥락:** 약 2,000건 × 사진 4장으로 최대 약 8,000장; 기존 R2 사용 중.
- **선택:** 비공개 버킷/접두사 + 서버에서 단기 presigned URL 발급 → 브라우저 직접 업로드 → DB에는 파일 키와 메타데이터 저장.
- **대안:** EC2 로컬 저장, DB BLOB, Spring Boot 프록시 업로드.
- **근거:** EC2 디스크·네트워크 부담 완화, 저장소 분리, 기존 자원 재사용.
- **트레이드오프:** CORS, 업로드 완료 검증, 고아 파일 정리, 파일 크기/확장자/MIME 검증, 사진 접근 제어 필요.
- **검증:** 실제 모바일 사진 4장 업로드, 비공개 다운로드 권한, 저장용량과 기존 서비스의 무료 할당량 합산 확인.

### ADR-007: 관리자 발급형 작업자 계정
- **상태:** 결정(구현 미완료)
- **맥락:** 소수 알바 중심이며 불특정 사용자 회원가입 필요 없음.
- **선택:** ADMIN/WORKER, 관리자가 계정 발급·비활성화·비밀번호 재설정.
- **대안:** 공개 셀프 회원가입, 소셜 로그인.
- **근거:** 운영 관리와 권한 통제가 간단하고 불필요한 가입·인증 기능을 줄임.
- **트레이드오프:** 계정 발급/초기 비밀번호 전달 절차와 퇴사 처리 필요.
- **검증:** 접근 통제, 비활성화된 계정의 세션 차단, 관리자 API 권한 테스트.

### ADR-008: 세션/쿠키 인증 우선 검토
- **상태:** 검증 필요(최종 미확정)
- **맥락:** 모바일 웹과 PC 관리자, 소수 사용자. 프론트 `pages.dev`와 API 도메인이 다를 수 있음.
- **후보:** Spring Security 세션(HttpOnly/Secure 쿠키), CSRF 및 SameSite/CORS 정책 명시.
- **대안:** JWT Access/Refresh Token.
- **근거:** 세션 폐기·계정 비활성화 제어가 간편하고 불필요한 토큰 갱신 코드를 줄일 수 있음.
- **트레이드오프:** 서로 다른 사이트 간 쿠키와 브라우저 추적방지 제약을 실제로 검증해야 하며, 불안정하면 인증 방식/도메인 배치 재검토.
- **검증:** 실제 Pages ↔ API 간 로그인 유지, 모바일 Safari/Chrome, CSRF·CORS 테스트.

### ADR-009: 엑셀 원본과 현장 입력의 분리
- **상태:** 설계 방향 결정 / 필드 구조 보류
- **선택:** 업로드 배치 및 `work_sites`의 기초 데이터, `work_records`의 현장 입력 및 완료 상태, `work_photos` 별도 저장. 초기 가변 필드는 JSONB 후보.
- **대안:** 모든 입력값을 한 테이블에 혼합, 전 필드 EAV.
- **근거:** 엑셀 재업로드, 현장 수정, 출처 추적, 원본과 입력값의 명확한 구분. 출력 시 두 데이터 결합.
- **트레이드오프:** JSONB에는 일관된 스키마 검증이 필요하며 잦은 필터 조건은 정규 컬럼/인덱스로 승격해야 함.
- **검증:** 실제 엑셀 컬럼, 고유키·중복 주소, 재업로드 업데이트 규칙, 보고서 예시 확인.

### ADR-010: 완료 이력·정산을 별도 모델로
- **상태:** 설계 방향 결정 / 정책 보류
- **선택:** 변경 이벤트/감사 로그 저장, 완료 시각·완료자 보존, 정산 단가는 해당 작업 시점에 스냅샷 저장. 낙관적 잠금과 중복 정산 방지 고려.
- **대안:** 작업자별 현재 완료 건수 × 현재 단가 계산만 사용.
- **근거:** 수정, 취소, 중복 완료가 있어도 지급 근거를 추적할 수 있음.
- **트레이드오프:** 상태 전이와 취소/재완료 규칙이 다소 복잡해짐.
- **검증:** 관리자 검수 여부, 완료 수정권한, 삭제 정책, 지급 확정 시점 확정.

### ADR-011: 출력 기능은 입력 모델 확정 후 개발
- **상태:** 보류
- **선택:** Apache POI 기반 엑셀 입출력 검토; HWPX 템플릿 및 라이브러리는 샘플 문서 확인 후 POC.
- **근거:** 표/이미지/페이지 레이아웃 요구에 따라 자동 생성 난도가 급변함.
- **검증:** 샘플 1건으로 파일 생성·열기·서식·사진 배치 테스트.

## 4. 문제 해결 로그 (실제 발생한 것만)

### ISSUE-001: Windows SSH PEM 파일 권한 오류 — 해결
- **증상:** `Permissions for 'C:\\KEYR.pem' are too open`, `bad permissions`, `Permission denied (publickey)`.
- **원인:** OpenSSH가 다른 사용자에게 읽기 가능한 개인키를 안전하지 않다고 보고 무시함.
- **조치:** Windows `icacls`로 파일 ACL 상속을 제거하고 현재 계정에 최소 읽기 권한만 부여.
- **결과:** SSH 접속 성공(사용자 확인).
- **면접 핵심:** 공개키 인증에서 개인키 접근권한이 왜 중요한지, Linux chmod와 Windows ACL 차이.

## 6. 포트폴리오용 서술 초안 (성과 확정 전)

## 2026-10-21 — ADR: 서버 세션 인증 및 프로파일 환경 분리 (구현 코드 작성, 실행 검증 대기)

### 상황
현장 작업자는 약 20명으로 관리자가 계정을 발급한다. 실제 데이터 입력 형식은 아직 확정되지 않았지만 로그인/회원 관리는 먼저 구현할 수 있다. 로컬 Windows와 EC2 운영 환경의 DB 주소 및 인증정보가 달라야 한다.

### 결정과 근거
- Spring Boot `local/prod` 프로파일로 DB 접속 대상을 분리한다. 비밀번호는 Git에 두지 않고 로컬은 IDE 환경변수, 운영은 서버 환경변수로 전달한다. `.env.local` 자동 로딩 라이브러리는 불필요하다.
- 회원가입 공개 API 대신 관리자 전용 작업자 생성/비활성화를 사용한다. 임시 비밀번호는 BCrypt로 저장하고 최초 변경 여부를 기록한다.
- JWT보다 Spring Security 서버 세션을 우선 적용한다. 사용자가 적고 웹 기반이라 리프레시 토큰 저장/회전 설계가 불필요하다는 장점이 있다. 단, 세션 저장소/다중 인스턴스 확장성은 제한된다.
- CSRF를 끄지 않고 토큰을 요구한다. 브라우저 세션 쿠키 인증에서는 CSRF 위험이 있기 때문이다.
- 기존 V1 Flyway `users` 테이블을 활용하여 신규 migration을 불필요하게 생성하지 않는다.

### 검토한 대안/트레이드오프
- JWT: 앱/분산 환경에 유리할 수 있지만 갱신·폐기 관리와 구현 부담이 증가.
- `.env.local` 파일 직접 로드: IDE 실행 시 편하지만 공통 설정에 import하면 운영도 같은 파일을 찾게 되어 프로파일 분리가 불명확.
- Vite 페이지 `pages.dev` + API 독립 도메인: cross-site 쿠키 정책으로 세션이 차단될 수 있어 운영에선 같은 사이트 도메인 구성 또는 프록시 필요.

### 작업 로그
- **작성 완료:** User/Role/Repository, 인증 상세 서비스, 관리자용 사용자 API, 변경 비밀번호 API, BCrypt, 로그인/로그아웃/CSRF 구성, local/prod YAML.
- **미검증:** Gradle 빌드, PostgreSQL Flyway 실행, 브라우저 쿠키/CSRF, 권한 제어 테스트.
- **남은 보안 과제:** 비밀번호 최초 변경 강제, 로그인 시도 제한, 관리자 작업 감사 로그, 운영 HTTPS/Cookie Secure 보장.

## 2026-10-21 — 요구사항 변경: A/B 검침 약 1년 분리 운영 (설계 검토 중)

### 고객 확인 사항
- **A(성과측정 시작단계)**: 2026년 11월부터 현장 입력 시작.
- **B(성과측정 완료단계)**: A로부터 약 1년 후, 2027년 무렵 별도 날짜에 입력.
- 따라서 `검침량(B-A)`은 B 기록이 준비되기 전까지 미산출/미확정 상태이다.

### 설계 영향과 근거
- **현장 작업 완료와 카드 최종 완료 분리**: A 수집을 끝냈어도 B가 없으면 최종 검침카드는 완료되지 않는다. 화면·통계에서 `A 대기/A 완료/B 대기/B 완료` 같은 단계별 진행 상태를 구분할 필요가 있다(상태 이름은 추후 결정).
- **데이터 모델**: 기초 수용가/급수전 정보와 회차별 측정값을 분리하는 방향을 우선 검토. 예: `work_sites`, `meter_readings(site_id, stage, reading_date, reading_value, worker_id, ...)`. `(site_id, stage)` 고유 제약은 동일 단계의 다회 측정 허용 여부 확인 후 결정한다. 사진은 원경/시작 근경/완료 근경/위치도를 구분한다.
- **정산**: A 완료만으로 정산하는지, B는 별도 작업으로 정산하는지, 반려/수정/교체 시 어떻게 조정하는지 고객 확인 전까지 확정하지 않는다.
- **데이터 정확성**: 측정값은 PostgreSQL `NUMERIC`, Java `BigDecimal` 후보. 계량기 교체, 역전/초기화, 결측, 재측정 상황을 설계 검토 항목으로 등록.
- **보고서 출력**: A만 존재할 때의 중간 카드 출력 허용 여부와 B 입력 후 최종 카드 출력 정책 확인.
- **운영 기간 리스크**: 초기 '2027년 초/중반 서비스 종료' 가정은 A/B 일정과 충돌한다. 적어도 B 수집·출력·인수인계까지 데이터 접근 가능해야 한다. AWS Free 플랜/크레딧 만료 대비 저장/복원/유료 전환 계획 재검토 필수.

### 확인된 요구사항
- 수용가/검침 건별로 **개별 한글 문서 1개씩** 생성하며, 최대 약 1,800건은 **ZIP 파일 하나로 다운로드**한다.
- 템플릿은 고객 제공 `붙임 2(검침카드 양식).hwp`이며, 관리번호·수용가 정보·A/B 검침값·검침량을 채우고 **위치도 1개 + 현장사진 3개**를 배치해야 한다.
- A는 2026-11부터, B는 약 1년 뒤 입력한다. B가 없을 때 출력 허용 여부는 미확정.

### 기술 방향 (구현 전 검증 필요)
- **첫 PoC**: Java `hwplib`로 제공된 `.hwp` 원본을 읽고, 텍스트 필드와 이미지 4개를 채워 원본 레이아웃을 유지한 채 한 건을 저장·재열기. 가능하면 필드/누름틀 기반으로 템플릿을 사전 정비. 실패 시 HWPX 변환 + `hwpxlib` 비교.
- **일괄 출력**: 완료된 개별 건을 차례로 조회 → R2에서 필수 이미지 가져오기 → 한 건 생성 → ZIP 엔트리에 추가 → 메모리 해제. 전체 데이터를 이미지까지 한꺼번에 적재하지 않음.
- **운영**: 작업 ID와 전체/성공/실패 건수·실패 사유·산출물 저장 키를 DB에 기록; 중복 실행 제한, 결과 다운로드 기한, 취소/재시도와 오류 보고서 고려. 비동기 작업은 초기에는 단일 서버 워커/DB 상태로 충분하며 별도 큐 도입은 추후 병목 시 검토.
- **자원**: t3.small RAM 2GiB 환경에서는 1건씩 생성하고 큰 ZIP은 임시 디스크/스트리밍 및 R2 업로드 방식의 부하 테스트가 필수. 이미지 4영역 중 하나는 위치도로서 사진 4장이라고 단정하지 않음.
- **파일명**: 고객 요구 확인 후 고유 관리번호 기반의 안전한 이름과 중복 방지 규칙 적용. ZIP 경로 조작 문자 제거.
- **보안**: 관리자만 대량 생성/다운로드 가능; 산출물은 비공개 R2에 저장하고 기한 짧은 서명 URL로 제공; 개인정보 포함 문서/임시 파일 정리와 다운로드 이력 관리.

### 대안 및 트레이드오프
- **개별 HWP+ZIP(선택됨)**: 1개 생성 재사용, 실패 단위 격리, 사용자별 파일 전달 용이. 파일 수와 압축 용량은 커질 수 있음.
- **1,800페이지 단일 HWP(비선택)**: 문서 병합·페이지·표/그림 위치 유지 복잡, 실패 영향 범위 큼.
- **즉시 HTTP 응답(보류)**: 소규모 출력에는 간단하나 대량에서는 타임아웃·연결 끊김 우려. 생성 Job 완료 후 R2 저장 권장.
- **HWPX 사용(대안)**: 내부 포맷 조작이 편하나 고객의 `.hwpx` 수용 여부와 변환 레이아웃 검증 필요.

### 확인/테스트 게이트
1. 원본 문서를 기반으로 **1건 완성**: 텍스트 교체, 4개 이미지 영역 교체, 한글 프로그램에서 원본과 비교.
2. 10건 → 100건 → 500건 → 1,800건 순 부하 시험: 소요 시간, 최고 메모리, ZIP 용량, 실패율, 사진 품질 측정.
3. B 미입력, 사진 누락, 계량기 교체, 재생성, 같은 관리번호, 특수문자 파일명, 누락·깨진 R2 이미지 처리 확인.
4. 11월 14일 납품에 포함되는 범위: A단계 중간 카드 출력인지 B단계 포함 최종 양식 엔진까지인지 고객 확인.

### 현 상태
- **요구 확정**: 개별 한글 문서 약 1,800개를 ZIP으로 전달.
- **선택된 설계 가설**: 템플릿 복제 기반 생성, 순차 처리, 비동기 ZIP 작업.
- **미완료/미검증**: HWP 원본 양식 수정 및 이미지 렌더링 PoC, 대량 부하 시험, 실제 ZIP 서비스 API. 면접·포트폴리오에 구현 완료로 기재하지 않는다.

## 2026-10-23 — 권한 요구사항 보완: 작업자는 본인 건수만, 금액 비공개

### 확인된 요구사항
- 정산/작업 내역 금액, 작업자 관리, 단가 설정 및 문서 출력은 관리자 전용이다.
- 작업자는 본인의 단계별 검침 건수를 확인하되 건당 단가와 합계 금액을 볼 수 없다. 금액은 관리자가 나중에 별도로 제공한다.

### 구현 및 검증
- 작업자 하단/PC 메뉴와 정산 바로가기에서 관리자 기능을 제거하고 hash 직접 접근도 관리자 전용 안내로 차단한다. 상세 검침 단가/합계 금액은 관리자일 때만 렌더링한다.
- 작업자 홈에 선택 블록 기준 본인 시작/종료 건수를 표시한다. 현재 Mock 작업자 ID는 11이다. 실제 로그인 사용자 연동은 후속 작업이다.
- MSW 작업자 sites/단건/저장 응답에서 fee 필드를 제거하고, users는 본인만 반환한다. 다른 작업자 명의 검침 등록을 거부한다. 관리자 API/단가/정산 API는 작업자 요청에 403을 반환한다.
- 브라우저의 관리자 모드 전환 버튼을 제거했다. 개발 중 관리자 확인은 VITE_DEMO_ROLE=ADMIN으로 서버를 실행하며 production 빌드에서는 이 설정으로 역할을 올릴 수 없다.
- 금액 필드 미포함, 관리자 API 403, 본인 사용자만 반환하는 회귀 검증 및 최종 빌드 통과. 브라우저에서 작업자 관리자 URL 접근 차단을 확인했다.

### 제한 및 후속 계획
- X-Demo-Role은 MSW 시연용 계약이며 위변조 방지 인증이 아니다. 운영 백엔드는 요청 헤더 역할을 신뢰하면 안 되며 서버 세션으로 관리자 권한과 실제 작업자 ID를 결정해야 한다. Java/DB는 이번 작업에서 수정하지 않았다.

## 2026-10-23 — ADR: 화면/업무 계층 분리, 대량 조회 및 조사자 계정 관리

### 상황
- App와 단일 CSS에 화면/상태/입력창이 집중되어 수정 범위와 스타일 충돌 파악이 어려웠다. 수용가는 구역당 수백 건, HWP는 1만 건을 넘을 수 있다. 관리자만 조사자 계정을 관리해야 한다.

### 결정과 근거
- App은 Provider와 앱 조립만 담당한다. pages, components, hooks, context, api, styles, mocks/handlers로 책임을 분리했다. 입력창 상태는 업무 컴포넌트에 두고 블록 조건은 공유한다. 기존 hash 경로와 React Query/MSW를 유지한다.
- 단일 CSS를 기본/레이아웃/공통/업무별 파일로 분리하고 index.css에서 순서를 명시한다. Prettier와 format:check로 줄바꿈 및 일관된 형식을 유지한다. 새 UI 라이브러리는 추가하지 않았다.
- 수용가/정산/조사자 목록은 페이지 조회, 통계와 일괄 단가 미리보기는 전체 대상 조회를 사용한다. 목록에서 사진 본문을 제외한다. 지도는 현재 페이지 최대 20개 마커만 대상으로 한다.
- HWP 파일명 나열을 제거하고 블록별 대상 건수만 제공한다. 실제 생성 버튼은 비활성이다. 과거 약 1,800개 가정은 최신 요구의 1만 건 이상으로 확장되었으며 생성 서비스 자체는 미구현이다.
- 조사자 생성/이름 수정/활성 상태/임시 비밀번호 초기화 UI와 관리자 전용 Mock 계약을 제공한다. 비밀번호 자체는 저장하거나 반환하지 않으며 실제 인증을 구현했다고 간주하지 않는다. 비활성 계정의 과거 검침 이력은 보존한다.

### 검증 결과와 한계
- npm run format:check, npm run test:api, npm run build 통과. TypeScript와 Vite 빌드 성공.
- 12,050건/603페이지, 소블록 4,018건, 페이지 간 중복 없음, 전체 집계 일치, 최대 페이지 크기와 경계값을 Mock 회귀 검증했다. 브라우저에서 1~20에서 21~40건으로 페이지 이동을 확인했다.
- 조사자 생성/대소문자 중복 거부/비활성 계정 검침 거부/재활성/비밀번호 길이 검사/응답 비밀번호 미포함/기존 실적 보존을 API 검증했다. 실제 로그인·임시 비밀번호 변경은 검증하지 않았다.
- 360/390/430/1280px iframe에서 9개 화면(홈, 목록, 지도, 관리자, 작업비, 정산, 출력, 조사자, 상세) 총 36개 조합을 확인했다. 모든 조합에서 문서 가로 넘침 없음. 세로 스크롤바가 있는 화면은 내부 폭이 15px 줄어든다. 실제 휴대폰 촬영/키보드는 미검증이다.
- 파일 이동 중 열린 탭에 과거 동적 import/HMR 오류가 남아 있었으며 새로고침 후 정상 표시됐다. 관리자 메뉴에서 조사자 관리 진입 및 작업자의 직접 접근 차단을 브라우저로 확인했다.
- 기존 ADR의 단일 App/클라이언트 미리보기/전체 목록 설명은 이 ADR로 대체된다. 이전 기록은 보존한다. Java/Flyway/DB는 수정하지 않았다.

### 트레이드오프 및 후속 계획
- 현재 공유 context는 화면 전환 시 필터 유지에 유리하지만 기능 확장 시 업무별 context로 세분화할 수 있다. 서버 연동 시 응답 계약과 인증 어댑터를 교체해야 한다.

### 사용자 요청 및 구현
- 마커가 지도를 가리는 문제에 따라 주황/초록 13px 점과 32px 클릭 영역으로 변경했다. 글자 배지와 큰 지도 안내문·조회 대상 이동 버튼을 제거하고 단계/상태 필터를 좁혔다.
- 마커/목록 선택 시 지도 아래에서 단건 상세를 조회하고 검침·사진·특이사항을 입력한다. 상세 경로 이동과 추가 입력 모달 없이 기존 API/검증을 재사용하며 각 영역을 별도로 저장한다. 미처리 검침 완료로 마커가 사라져도 선택 폼을 유지한다.
- 지도와 상세 화면의 사진 칸 클릭이 시스템 이미지 선택기를 직접 연다. capture를 강제하지 않아 OS가 제공하는 촬영/갤러리 선택을 사용한다. 메뉴 구성과 실제 촬영 결과는 기기별 확인이 필요하다.
- NAVER JavaScript SDK의 공식 컨트롤 목록에는 앱과 동일한 GPS 컨트롤이 없다. 기존 Geolocation 감시를 유지하고 지도 내부 GPS 아이콘, 파란 점의 맥동 효과, 접이식 위치 오류 안내로 축소했다. SDK 기본 기능으로 오인하지 않는다.
- 현재 페이지 최대 20건과 블록/단계 필터 계약은 유지했다. 수백 건 동시 조회·클러스터링은 이번 변경에서 구현하지 않았다. 이전 기록의 큰 배지/조회 대상 보기/상세 이동 UI 설명은 이 기록으로 대체된다.

### 검증과 한계
- npm run format:check, npm run test:map, npm run test:api, npm run build, demo 플래그를 실행 환경에 주입한 npm run build:demo 통과.
- 브라우저에서 마커 클릭 → 지도 내 검침 저장(가상 지침 125) → 미처리 8건에서 7건 및 폼 유지 → 사진 칸 직접 선택/저장 → 특이사항 저장 → 닫고 재선택 후 세 영역 재조회 확인. 실제 고객 사진 대신 기존 가상 데이터 지도 캡처를 테스트 이미지로 사용했다.
- 390px 뷰포트에서 지도·사진·특이사항 배치와 문서 가로 넘침 없음 확인. 위치 권한 거부 안내 확인. 실제 휴대폰 카메라/갤러리 메뉴 및 GPS 성공은 미검증이다.
- 백엔드/DB/환경파일 변경, 원격 배포, 커밋·푸시는 없다.
