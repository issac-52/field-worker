# HWPX 검침카드 다운로드

## 사용 방법

관리자 `문서 출력`에서 전체/선택 중·소블록을 대상으로 **검침카드 생성 요청**을 누른다. 수용가 상세 화면에서도 해당 수용가 한 건을 요청할 수 있다. 문서 상단 사업명은 요청 시 입력한다. 제목은 문서 내용과 캐시 키에 포함된다.

화면을 닫아도 서버에서 계속 처리한다. 같은 관리자 계정으로 `최근 생성 요청`을 열어 진행 상황과 파일을 확인한다. 출력은 수용가별 `site-{id}.hwpx`를 담은 ZIP이다. 한 묶음은 최대 50건이며 압축 결과가 약 16MiB를 넘으면 더 일찍 분할한다(마지막 문서의 크기만큼 초과 가능). 내부 분할은 서버 생성/보관용이다. 전체 생성이 완료되면 사용자는 **ZIP 하나로 전체 다운로드**한다. 기존에 생성 완료된 작업도 재생성 없이 전체 다운로드할 수 있다. 실행 중 데이터가 변경돼 실패하면 다시 요청하며, 앞서 만든 유효한 개별 문서는 재사용한다.

## 양식과 데이터

사용자가 제공한 빈 HWP를 HWPX 템플릿으로 변환했고 원래 표/셀 구조와 서식을 유지했다. 개인정보 Excel은 포함하지 않았다. 성명/주소/관리번호/업종/계량기번호/특이사항/START·END 날짜와 지침/사용량을 입력한다. 원본 AZ 급수전번호가 있으면 사용하고 없으면 수용가번호를 사용한다. 공급 자료에 매핑이 없는 급수구역/봉인은 미기재/미확인으로 표시한다. 미등록 검침은 빈칸이며 0으로 만들지 않는다.

사진은 OVERVIEW, START_CLOSEUP, END_CLOSEUP만 포함한다. 위치도 칸은 비워 두며 지도 검색이나 지도 이미지 API를 호출하지 않는다. 임시/추가 사진은 양식에 넣지 않는다. 원본 사진을 변경하지 않고 문서용 사본만 최대 1280px로 축소하고 JPEG로 넣는다. 비율을 유지하며 EXIF 방향을 반영한다.

`backend/src/main/resources/hwpx/card-template.hwpx`가 양식이다. 양식/생성 로직 변경 시 `HwpxCardRenderer.VERSION`을 변경해야 기존 캐시를 재사용하지 않는다. 변환 도구 출처/라이선스는 같은 디렉터리 README에 기록했다.

## 생성·보관·변경 처리

- V9 마이그레이션에서 작업/항목/결과/캐시 메타데이터 테이블만 추가한다. V1~V8은 변경하지 않는다.
- 처음부터 19,000개 문서를 만들지 않는다. 요청된 ID 목록을 작업에 고정하고, 각 문서를 만들 때 DB의 단일 SQL 스냅샷을 읽는다. 전체 작업이 하나의 시점으로 동결되는 것은 아니다.
- 기본정보·검침·사용 사진의 저장 객체 키와 양식 버전·사업명으로 SHA-256 키를 계산한다. 같은 내용이면 저장된 HWPX를 재사용한다. 사진 교체/삭제와 검침 정정은 새 문서로 이어진다.
- HWPX/ZIP은 기존 ObjectStorage를 이용해 운영에서는 비공개 R2에 UUID 키로 저장한다. EC2에 영구 문서 디렉터리를 만들지 않는다. 한 작업당 최대 50,000건, 서버 전체 대기/실행 작업은 최대 3개다.
- 백그라운드 작업은 DB에 저장된다. 서버 재시작 후 완료된 ZIP 다음부터 이어간다. DB advisory lock으로 동시에 한 작업 묶음만 생성한다. 생성 실패 사유에는 개인정보나 저장소 키를 노출하지 않는다.
- 작업/결과/개별 문서의 보관 기간은 각각 생성 후 7일이다. 만료 결과는 다운로드할 수 없고, 실제 객체 삭제는 기존 삭제 대기열을 통해 재시도한다. 장기 보관이 필요한 결과는 내려받아 보관한다.
- 다운로드 직전에 해당 ZIP의 원본 데이터 해시를 다시 비교한다. 사진/정보가 달라졌으면 EXPORT_STALE(409)로 다운로드를 막고 재생성을 안내한다. 이미 사용자가 내려받은 파일은 회수할 수 없다.

## 사진 삭제와 R2

기존 사진 삭제/교체는 트랜잭션에서 DB 참조를 지우고 `photo_deletions`에 객체 키를 넣는다. 기본 60초 주기의 PhotoCleanup이 R2 삭제를 호출하며, 실패하면 대기열을 보존해 재시도한다. 문서 생성과 겹쳐도 삭제 작업이 실행되도록 scheduling pool size=2를 설정했다.

삭제된 사진이 들어 있던 과거 HWPX/ZIP 캐시는 원본 사진 객체와 별개다. 다운로드 시 변경 검사로 차단되며, 저장소의 문서 사본은 7일 보관 기간 만료 후 정리된다. 운영 R2 버킷 정책/삭제 권한 때문에 실패하면 지연될 수 있으므로 삭제 대기열과 서버 로그를 확인한다.

## API / 권한

모두 기존 `/api/exports/**` ADMIN 권한을 따른다. 작업 조회·다운로드는 요청한 관리자만 가능하다. 생성 POST는 CSRF가 필요하다.

- POST `/api/exports/cards`: `{siteId?,middleBlock?,smallBlock?,title}` → `{id}`
- GET `/api/exports/cards`: 최근 20개, 만료 전 본인 작업
- GET `/api/exports/cards/{id}`: `{id,title,status,total,completed,error,parts:[{part,firstOrdinal,lastOrdinal}]}`
- GET `/api/exports/cards/{id}/download-check`: 완료/만료/전체 원본 변경 검사
- GET `/api/exports/cards/{id}/download`: 모든 내부 ZIP을 순서대로 읽어 HWPX가 직접 들어 있는 ZIP 하나로 스트리밍. 전체 Blob을 브라우저 메모리에 만들지 않고 브라우저 기본 다운로드로 저장한다. 서버도 한 내부 묶음씩 읽는다.
- GET `/api/exports/cards/{id}/parts/{part}`: 기존 호환용 개별 묶음 API, 화면에서는 사용하지 않는다.

전체 다운로드는 READY만 가능하며 단일 커서 SQL로 원본 해시를 검증한다. 전송 도중 저장소/네트워크가 끊기면 다운로드가 실패할 수 있고 자동 이어받기는 지원하지 않는다. 19,600건 실환경 전송 시간 및 Cloudflare 경로의 대용량 전송은 별도 검증이 필요하다.

상태는 QUEUED/RUNNING/READY/FAILED. 프론트는 진행 중일 때만 2초 간격으로 상태를 확인한다. 스토리지 공개 URL이나 자격 증명을 응답하지 않는다.

## 배포와 검증 범위

새 환경변수는 필수가 아니다. 기존 prod R2 설정을 사용하며 새 JAR와 프론트 배포가 필요하다. `app.documents.worker-enabled=false`는 생성 작업을 멈추는 운영/테스트 옵션이며, 기본값은 true다. worker-delay-ms 기본 1000ms. 만료 정리도 이 작업에서 수행한다.

Java 21/PostgreSQL 통합 테스트에서 생성·캐시 재사용·51건 분할·중단 작업 재개·보관 만료·ADMIN/CSRF/소유자 권한·사진 삭제 후 과거 ZIP 차단을 확인했다. 로컬 ObjectStorage로 원본 사진 삭제 대기열/정리 동작을 검증했고 삭제 실패 재시도는 대역 테스트로 확인했다. 실제 R2 호출은 실행하지 않았다.

생성 HWPX는 ZIP/XML 검사와 hwpxlib 1.0.9 독립 읽기 검증을 통과했다. 실제 한글 프로그램에서의 열기/인쇄 페이지·글꼴·긴 주소 줄바꿈은 미검증이다. 가상 데이터 샘플은 `backend/build/validation/fictional-inspection-card.hwpx`에 테스트가 생성한다. 19,000건 전체 부하·운영 저장소 소요 시간은 아직 측정하지 않았다.

## 생성 취소와 결과 삭제 (2026-11-09)

`최근 생성 요청`에서 기존 요청별 상태/처리 건수와 **생성 취소**, **결과 삭제** 버튼을 제공한다. 중복으로 접수한 기존 요청도 같은 방식으로 관리한다.

- POST `/api/exports/cards/{id}/cancel`: 대기/진행 작업을 CANCELLED로 바꾼다. 현재 한 건 처리 중이면 그 건을 마친 후 멈추며, 취소 뒤 다음 묶음으로 재개하거나 완료 상태로 덮어쓰지 않는다. 이미 완성한 묶음과 개별 캐시는 보존한다. 완료 작업 취소는 409이고 삭제를 이용한다.
- DELETE `/api/exports/cards/{id}`: 작업을 취소하고 delete_requested를 설정한다. 화면에는 DELETING으로 보이며 요청은 즉시 반환한다. 생성 워커의 DB 잠금이 해제된 후 정리 작업이 작업/항목/ZIP 메타데이터를 제거하고 실제 저장소 객체는 기존 삭제 대기열에서 재시도한다.
- 같은 수용가를 포함하는 다른 유효한 미삭제 작업이 있으면 해당 수용가 캐시를 보수적으로 보존한다. 두 요청을 모두 삭제해 참조가 없어지면 캐시와 작업 ZIP도 삭제 대기열에 넣는다. 원본 사진·수용가·검침 데이터는 삭제하지 않는다.
- ADMIN/요청자 소유권 및 CSRF 검사를 적용한다. 삭제는 UI 확인 후 수행한다. 이미 사용자가 내려받은 파일은 삭제하지 못한다.

V10만 추가하며 V1~V9는 변경하지 않는다. 기존 작업에는 delete_requested=false 기본값이 적용된다. 생성 기능을 `app.documents.worker-enabled=false`로 중지해도 별도 DocumentMaintenance가 2초 주기로 삭제/만료 정리를 시도한다. 실제 객체 삭제는 PhotoCleanup 기본 60초 주기 및 저장소 상태에 따라 지연될 수 있다. 테스트용 `app.documents.maintenance-enabled=false`는 정리도 멈추므로 운영에서 설정하지 않는다.
