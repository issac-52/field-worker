# 수용가번호 미등록 자료 지원

상태: 구현 및 개발 환경 검증. 운영 DB 적용·배포는 수행하지 않았다.

## 식별 규칙

- PK는 계속 자동 생성 내부 `worksites.id`다. 사진·검침·이력·문서는 이 ID를 사용한다.
- 번호가 있는 행은 기존처럼 `consumer_number`로 식별하며 중복을 허용하지 않는다.
- 번호 없는 행은 SQL NULL로 저장한다. **번호 없는 수용가끼리 새주소(E열) + 수용가명(D열)**이 모두 일치하면 같은 대상으로 본다.
- 주소·이름의 앞뒤 ASCII 공백을 제거하고 연속 공백/탭/개행을 한 칸으로 정리해 비교한다. 저장·표시되는 원문은 유지한다. 대소문자·구두점·주소 약칭을 임의 변환하지 않는다.
- 새주소 또는 이름이 비면 `MISSING_ADDRESS_OR_NAME`으로 해당 행을 제외한다. 번호가 있으면 기존처럼 이름/주소가 비어도 등록할 수 있다.
- 이름이 같아도 주소가 다르거나 주소가 같아도 이름이 다르면 별도 수용가다. 번호가 있는 기존 수용가와 번호 없는 행을 주소·이름만으로 합치지 않는다.
- 번호 없는 서로 다른 실제 수용가가 주소·이름까지 같으면 현재 정책으로 구분할 수 없다. 이 경우 수용가번호를 제공해야 별도 등록할 수 있다.

## 업로드·보완

같은 파일 안에서는 식별 기준별 최초 행만 사용한다. 중복 제외 보고서의 최초 시트/행 번호는 유지한다. 보이는 행만 업로드할 때는 숨김 제외를 먼저 적용한다. 재업로드는 이미 등록된 동일 식별 자료를 추가 등록하지 않는다.

빈 기본정보 보완도 같은 식별 기준으로 찾는다. 번호가 없으면 번호 없는 DB 수용가 중 새주소·이름이 같은 자료만 보완하며 신규 생성·번호 자동 배정·기존 값 덮어쓰기는 하지 않는다. 사진·검침·좌표·정산은 그대로 둔다.

번호 없는 행의 주소·이름을 바꾸어 재업로드하면 새로운 식별 대상으로 간주한다. 기존 수용가를 수정/병합하는 동작이 아니다.

## 나중에 실제 번호 등록

관리자는 상세 화면의 **수용가번호 등록** 버튼으로 번호가 없는 수용가에 실제 번호를 부여할 수 있다.

- `PATCH /api/admin/sites/{id}/consumer-number`, body `{consumerNumber:"00012"}`.
- ADMIN·CSRF 필수. 앞뒤 공백을 제거한 1~100자 문자열을 받으며 선행 0을 유지한다.
- 이미 사용 중인 번호는 `CONSUMER_NUMBER_CONFLICT`(409), 이미 번호가 있는 수용가는 `CONSUMER_NUMBER_ALREADY_SET`(409).
- 내부 ID/사진/검침은 유지하고 번호 등록을 변경 이력에 남긴다. 번호를 덮어쓰거나 지우는 기능은 제공하지 않는다.
- 등록 후에는 번호로 식별하므로 **이후 재업로드할 Excel에도 등록한 번호를 반영**한다. 예전 번호 없는 행을 자동으로 번호 있는 자료에 연결하지 않는다.

## 숨김 수용가 삭제

숨긴 행의 식별 기준도 동일하다. 보이는 행에도 같은 식별 값이 있으면 보존하며, 파일 밖의 DB 자료는 삭제하지 않는다. 번호 없음 자체는 제외 사유가 아니다. 번호도 없고 주소·이름도 부족한 행은 삭제 대상에서 제외한다.

미리보기는 내부 ID 유지 집합을 `keep_site_ids`에 저장한다. 실행 시 데이터 지문·정산 보호·확인 문구·소유권·15분 만료를 다시 검증한다. 확정/지급 정산이 있으면 전체 삭제를 차단한다. 연관 사진·미확정 검침 및 문서 정리 정책은 [기존 삭제 문서](VISIBLE_EXCEL_AND_PRUNE.md)를 따른다.

응답은 기존 `scope=HIDDEN_ROWS`에 `identityVersion=2`를 추가한다. `hiddenRowsWithoutIdentity`, `visibleRowsWithoutIdentity`, `visibleDuplicateIdentities`, `unmatchedHiddenIdentities`를 추가하고 sample에 `id`, `name`, `address`를 제공한다. 기존 번호 관련 집계 필드는 호환용으로 남기되 UI는 식별 기준 집계를 사용한다. **이전 방식으로 만든 미실행 계획은 재미리보기를 요구한다.**

## DB 변경과 검증

V12만 추가했다. 기존 V1~V11을 수정하지 않았다. 수용가번호 NOT NULL을 해제하되 기존 UNIQUE/빈 문자열 제한을 유지한다. 번호 없는 자료는 주소·이름이 필수이며 정규화한 두 값에 부분 UNIQUE 인덱스를 둔다. 애플리케이션의 파일 중복 검사와 별개로 동시 업로드 중복도 DB가 차단한다.

실제 실행:

```bash
bash backend/gradlew -p backend test bootJar --no-daemon
bash backend/gradlew -p backend test --tests '*GeocodingIntegrationTest' --no-daemon
cd frontend
npm run typecheck
npm run lint
npm test
npm run build
```

- 기존 코드에서 번호 없는 등록·재업로드·동시 등록·보완·삭제·문서 관련 신규 테스트 5개 실패를 확인한 뒤 수정했다. 관리자 번호 등록 API도 미구현 실패를 확인한 뒤 구현했다.
- 전체 PostgreSQL 회귀 및 JAR 빌드 성공. V11→V12 업그레이드에서 번호 있는 자료 보존, 주소·이름 UNIQUE/필수 제약을 검증했다.
- 번호 없는 자료의 지오코딩 성공·서비스 오류·권한·할당량을 기존 8개 테스트에 포함해 추가 재검증 성공. 실제 NAVER 호출은 하지 않았다.
- 프론트 typecheck/lint/test 26개/build 성공. Chromium 합성 API 390/1440px에서 미등록 표시, 번호 등록·중복 거부·CSRF·선행0·새로고침, 신규 오류 표시와 번호 없는 삭제 미리보기를 확인했다.
- 원본 개인정보 Excel 수동 테스트는 이번 작업에서 실행하지 않았다. 가상 XLSX와 독립 PostgreSQL, 메모리/로컬 파일 저장소만 사용했다. 실제 R2/운영 대량 업로드·삭제는 미실행이다.
