# 최종 Excel 양식 및 기본정보 업데이트 — 2026-11-17

## 화면 사용

관리자 메뉴 → 수용가 Excel 등록에서 **엑셀 양식**과 **업로드 방식**을 선택한다. 신규 기본값은 `신규 양식 (최종본 · 3행 헤더)` + `신규 등록 + 기존 기본정보 업데이트`다. 새 백엔드와 프론트 배포 이후 사용할 수 있다.

- 신규 양식 `FINAL`: `@@@수용가 전수(검침조사)` 시트만 읽는다. 3행 헤더 아래부터 읽고 참고·집계·다른 수용가 시트는 전부 제외한다. 대상 시트가 없거나 선택한 양식과 헤더가 다르면 400으로 전체 업로드를 롤백한다.
- 구 양식 `LEGACY`: 기존 2행 C=수용가번호/D=수용가명/E=새주소 및 기존 열 배치를 유지한다. 기존 다중 시트 검증을 유지한다.
- `신규 등록 + 기존 기본정보 업데이트`: 번호가 있으면 없는 번호는 등록, 기존 번호는 기본정보의 **비어 있지 않은 값**을 반영한다. 실제 차이가 없으면 변경 없음으로 집계하고 수정 시각/이력을 추가하지 않는다. 빈 값으로 기존 값을 지우지 않는다. 같은 파일의 같은 번호는 첫 행만 처리하고 나머지는 원본 행 번호와 함께 파일 중복으로 보고한다.
- `신규 수용가 등록`: 기존과 동일하게 기존 번호를 건너뛴다.
- `빈 기본정보 보완`: 기존 번호의 빈 값만 보완하며 기존 값은 덮어쓰지 않는다. 신규 등록하지 않는다.
- 번호 없는 행은 이름 없이도 새주소로 신규 등록할 수 있다. 이미 등록된 주소면 `DUPLICATE_ADDRESS_WITHOUT_NUMBER`, 주소도 없으면 `MISSING_ADDRESS`다. 주소로 기존 행을 찾아 업데이트하거나 병합하지 않는다. 빈 정보 보완에는 번호가 필요하다.

업로드는 자동 삭제를 하지 않는다. 기존 보이는 행 옵션은 두 양식에서 모두 적용한다. 숨김 수용가 삭제 미리보기도 선택한 양식을 전달하며 기존 미리보기/확인/정산 차단 정책을 그대로 적용한다. 양식·파일·처리 방식 변경 시 이전 미리보기를 폐기한다.

## 신규 양식 매핑

기존 DB 컬럼 및 `source_cells` 조회 계약에 맞게 기본정보만 정규화한다. 원본 전체 XLSX를 DB나 Git에 저장하지 않는다.

| 신규 Excel | 항목 | 기존 저장 키 / DB |
| --- | --- | --- |
| C | 수용가번호 | C / consumer_number |
| D | 수용가명 | D / name |
| E | 새주소 | E / address |
| F | 주소 | F / old_address |
| L | 업종 | I / industry |
| M | 구경 | J / source_cells |
| N | 가구수 | K / source_cells |
| Q | 하 | L / source_cells |
| AC | 상호 | AX / source_cells |
| AD | 계량기번호 | G / meter_number |
| AE | 수전번호 | AZ / source_cells |
| AF | 대블럭 | B / middle_block (기존 중블록 조회 항목) |
| AG | 소블럭 | BB / small_block |
| AH | 검침담당 | BC / source_cells |
| AI | 정례검침일 | BD / source_cells |
| AJ | 관리번호 | BE / management_number |

신규 G=원격, H=계량기철거 등 새로 생긴 참고 항목은 가져오지 않는다. 특히 H는 구 양식의 계량기 유무와 의미가 다르므로 매핑하지 않는다. 기존 계량기 유무/비고 값은 신규 양식 업로드로 삭제하지 않는다. 월별 사용량 R:Z와 기타 미지원 열도 무시한다. 구 양식의 H 분류(정확히 완료일 때 유무, 그 외 비고)는 유지한다.

## 보존 및 이력

기존 수용가는 수용가번호로 찾고 같은 DB PK를 유지한다. import된 기본 컬럼과 위 표의 정규화된 source_cells만 업데이트한다. 사진/R2 객체, START/END/검침 이력, 확정·지급 정산/단가/금액, 현장 메모·특이사항은 변경하지 않는다. 좌표 변환에 실제 사용하는 주소가 바뀌면 위도·경도를 함께 NULL로 초기화하고 전후 이력을 남긴다. 주소 비교는 지오코딩과 동일하게 새주소의 앞뒤 공백을 제거하고, 새주소가 비면 구주소를 사용한다. 새주소가 유지되고 구주소만 바뀐 경우와 주소 앞뒤 공백만 바뀐 경우에는 좌표를 유지한다. 엑셀의 빈 값은 기존 주소를 지우지 않으므로 좌표도 비우지 않는다. API를 업로드 중 호출해 자동 변환하지 않으며, 지도에서 해당 조건의 주소로 좌표 등록을 다시 실행하면 새 주소로 좌표를 저장한다. 검색 결과가 없으면 좌표는 미등록 상태로 남는다. 이 초기화는 신규등록+기존업데이트 방식에 적용하고 기존 빈 정보 보완 방식의 좌표 보존 정책은 유지한다.

변경된 기본정보/원본 키와 주소 변경으로 초기화한 좌표를 `worksite_edits`에 전후 이력으로 남긴다. 기존 import 출처의 sheet/row/job 메타데이터는 유지한다. 원본 내용 변경에 대한 기존 HWPX 스냅샷 검사도 유지된다. 업데이트로 원본 해시가 달라진 기존 문서는 다운로드 시 재생성 안내를 받는다.

모든 등록·업데이트·보완은 기존 업로드 advisory lock을 공유한다. 검증 실패 시 해당 요청의 등록/수정/이력 전체를 롤백한다. Flyway 및 기존 V1을 수정하지 않는다.

## API 호환

- POST `/api/admin/imports`: multipart `file`, `visibleOnly=false`, `format=LEGACY`, `updateExisting=false`. 새 화면은 선택값을 명시적으로 보낸다. 생략한 기존 API 호출은 구 양식/등록 전용 동작을 유지한다.
- 응답 기존 필드에 `updated`, `unchanged` 정수 추가. `inserted`는 신규 등록만, `updated`는 실제 변경만 센다. 오류·파일 중복만 제외 행 표에 표시한다. 기존 API 결과 조회도 동일 집계를 보관한다.
- POST `/api/admin/imports/repair`, `/api/admin/imports/prune/preview`도 multipart `format=LEGACY`를 받는다. 보완/삭제 자체 정책은 변경하지 않는다. 잘못된 format 값은400이다.
- 기존 ADMIN/최초 비밀번호 변경/CSRF 검사를 유지한다.

## 개별 한글 파일명

기존대로 `site-{worksites.id}.hwpx`다. 목록 순번이 아니라 **DB PK**이므로 범위·정렬·배치 크기가 바뀌어도 동일 수용가는 같은 이름을 갖는다. 관리번호는 DB에서 일반 인덱스만 있고 UNIQUE가 아니므로 파일 식별자로 사용하지 않는다. 기존 캐시/생성 파일명을 변경하거나 일괄 재생성하지 않는다. 엑셀 내보내기는 기존대로 전체 `fieldwork.xlsx` 한 파일이다.

## 검증

신규 통합 테스트3개 중2개가 기존 구현에서 실패하는 것을 확인한 뒤 구현했다. 합성 테스트에서 신규 대상 시트 선택/원본 행 번호/열 매핑/월별 제외/중복 첫 행/같은 PK 업데이트/사진·좌표·확정 검침 보존/빈 값 보존/동일 업로드 재실행/신구 오선택/숨김 제외/번호 없는 주소 중복을 검증한다. 전체 테스트와 화면 결과는 아래 실행 기록을 함께 참고한다.

별도 opt-in `FinalWorkbookValidationTest`로 제공된 최종본을 임시 PostgreSQL에 실제 등록했다. 개인정보와 원본 XLSX는 커밋하지 않고 집계만 남긴다.

- 최초: 검사18,541 / 등록18,541 / 파일 중복0 / 오류0.
- 재업로드: 등록0 / 업데이트0 / 변경 없음18,522 / 번호 없는 기존 주소 오류19. PK/건수 유지와 DB 기본정보·정규화 셀 일치를 확인했다.
- 이 결과는 **빈 임시 DB** 기준이다. 현재 운영 DB와의 대조 또는 실제 운영 반영은 수행하지 않았다. 운영에서는 기존 번호·주소 분포에 따라 등록/업데이트/오류 집계가 달라진다.

실행 명령(Java21/Docker 환경):

```bash
bash backend/gradlew -p backend test bootJar --no-daemon
FIELDWORK_EXCEL_PATH=/private/final.xlsx bash backend/gradlew -p backend manualExcelTest --tests '*FinalWorkbookValidationTest*' --no-daemon
cd frontend
npm run typecheck
npm run lint
npm test
npm run build
npm run format:check
```

업로드 중 기존 번호를 조회해 기본정보를 비교하는 방식으로, 약2만 건에서 운영 DB/네트워크 소요 시간은 별도 관측해야 한다. 비동기 대량 업로드 API로 전환한 것은 아니다.

실제 최종 실행 결과: PostgreSQL 회귀104개 실패/오류/skip0 및 test bootJar 성공. 앞선 커밋에서 opt-in 최종본 검증1개 성공. 프론트 typecheck/lint/테스트27개/build/format:check 성공. 로컬 Chromium의 합성 API로390/1440px에서 양식/방식 선택, 등록·보완·삭제 미리보기 multipart의format/updateExisting/CSRF, 결과 집계와 미리보기 초기화, 가로 넘침/콘솔 오류 없음을 확인했다. 실제 운영 API를 통한 최종본 업로드 및 배포는 수행하지 않았다.

주소 변경 좌표 초기화 추가 검증: 신·구 양식 각각 새주소 변경/대체 구주소 변경/실제 입력 주소 유지의6개 사례 중 기존 구현에서 초기화4개 실패를 확인했다. 수정 후 전체104개 성공 및 JAR 빌드 성공. 새 주소를 GeocodingService에 전달해 미등록 대상 조회부터 새 위도·경도 저장과 이력까지 임시 PostgreSQL에서 검증했다. 외부 Geocoding API는 대역을 사용했으며 실제 NCP 호출/운영 DB 변경은 하지 않았다. 프론트 안내 문구 수정 후 format:check/typecheck/27개 테스트/build도 성공했다.


## 최종본에 없는 수용가 정리

관리자 엑셀 등록에서 신규 양식과 신규 등록 + 기존 기본정보 업데이트를 선택하고 최종본으로 등록·업데이트한다. 완료 후 같은 화면에서 삭제 대상 미리보기를 열고, 연결 사진·검침·문서 건수와 예시를 확인한 뒤 확인 문구를 입력해 삭제한다. 엑셀 파일은 최대 50MiB(요청 전체 51MiB)이며, 압축 해제 시 큰 시트는 디스크 기반으로 읽는다.

이 비교는 대상 시트의 숨김 여부와 관계없이 모든 행을 포함한다. 기존 수용가번호는 번호가 같은 행이 있으면 유지한다. 번호 없는 DB 수용가는 새주소를 정규화해 최종본 행의 새주소와 대조한다. 주소가 비어 식별할 수 없는 기존 자료는 유지한다. 엑셀 내 중복 번호, 번호와 주소가 모두 없는 행, DB와 공통 수용가번호가 없는 파일은 미리보기를 진행할 수 없다.

기존 숨김 행 삭제와 동일하게 미리보기는 15분 동안 유효하고 DB 상태가 바뀌면 다시 만들어야 한다. 확정·지급 정산이 연결된 대상이 있으면 삭제 전체를 차단한다. 확인 단계에서 대상 수용가와 연결 기록을 정리한다.
