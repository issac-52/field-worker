# 2026-11-10 성능 기준 측정

공유용 자료: [PDF·프로젝트 개요·그래프](portfolio/performance-baseline/README.md), [후속 개선 기록](portfolio/performance-baseline/IMPROVEMENT_LOG.md).

## 결론

운영 변경 없이 가상 수용가 20,000건으로 측정했다. 목록 조회의 행별 추가 SQL과 사진이 있는 한글 생성이 우선 조사할 지점이다. Redis나 메시지 시스템 도입에 앞서 목록 쿼리와 문서 생성 경로를 개선하고 같은 조건으로 재측정하는 것을 권한다. 이번에는 개선을 적용하지 않았다.

## 범위와 재현

- 측정 대상: `develop` 커밋 `4768ab313d2e814baf20f200263071db2441db97`의 서비스/지도 컨트롤러와 JSON 직렬화. HTTP 서버, 인증 필터, 브라우저, Cloudflare, 실제 R2/NAVER는 제외했다.
- Java 21.0.13, PostgreSQL 17-alpine Testcontainers, Hikari 풀 10개, JVM 최대 힙 768MiB. 개발 환경 CPU 할당 2개, 컨테이너 메모리 한도 8GiB. 운영 EC2와 다른 환경이다. CPU 사용률/최대 RSS/GC 프로파일은 이번에 수집하지 않았다.
- 가상 수용가 20,000건, START 10,000건, END 5,000건. 좌표는 제한된 영역에 규칙적으로 분포한다. 운영 주소·이름·사진·Excel은 사용하지 않았다.
- 문서 대상 100건에는 각각 사진 3장(합성 JPEG 1600×1200, 장당 362,834바이트)을 연결했다. 저장소는 로컬 파일이며 추가 지연은 0이다. 생성물과 DB 컨테이너는 종료 시 정리한다.
- 목록/요약은 실제 서비스와 동일하게 읽기 트랜잭션을 적용했다. SQL 횟수는 JDBC execute 호출 수이며 executeBatch는 1회로 센다. JDBC 시간에는 결과 매핑과 일부 fetch 시간이 포함되지 않는다.
- 읽기는 시나리오별 2~3회 예열 후 10~20회 측정했다. 짧은 표본이므로 p95는 참고치이며 운영 SLO나 처리 한계로 해석하지 않는다.

Java 21과 Docker가 있는 환경에서 저장소 루트에서 실행한다.

```bash
bash backend/gradlew -p backend performanceBaseline --no-daemon
bash backend/gradlew -p backend test --no-daemon
```

사진 없는 생성기만 재측정하려면:

```bash
bash backend/gradlew -p backend performanceBaseline --tests '*PerformanceBaselineTest.rendererWithoutPhotos' --no-daemon
```

결과는 `backend/build/performance/`에 기록된다. 일반 `test`에서는 performance 태그만 별도로 제외하며 기존 회귀 테스트는 그대로 실행한다. 테스트용 DB 접속은 Testcontainers가 생성하며 운영 환경변수를 읽지 않는다.

### 실행 계획

`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 단회 실행 결과:

- 목록 ID 첫 20개: `worksites_management` Index Only Scan, 0.033ms.
- 네 열 부분 문자열 검색 count: Seq Scan, 24.593ms. 20,000행 검사 중 111행 일치.
- 지도 전체 영역 집계: Seq Scan, 22.144ms, 20,000행 처리. 합성 분포에서 집계 결과는 6개였다.
- 좁은 지도 영역 ID 조회: Seq Scan 및 정렬, 3.422ms. 일치 25행, 제외 19,975행. 이 계획은 검사 상태 하위 쿼리를 제외한 좌표/정렬 부분만 대상으로 하며 전체 마커 API 시간과 동일하지 않다.

## 한글 결과

| 시나리오 | 측정 범위 | 결과 |
| --- | --- | ---: |
| 사진 3장씩 있는 100건 최초 생성 | DB/사진 읽기/생성/캐시 저장/ZIP 생성 | 48.47초 |
| 같은 100건 재요청 | 기존 HWPX 캐시 읽기/새 ZIP 생성 | 2.03초 |
| 사진 없는 문서 | 생성기만, 5회 예열 후 100회 | 건당 p50 6.42ms / p95 18.01ms |

100건 작업은 최초/재요청 각각 **1회만** 측정했다. 원시 JSON의 p50/p95는 단일 관측값과 같으며 통계적 백분위로 해석하면 안 된다. 작업 tick을 연속 호출했으므로 실제 스케줄러 대기(1초 간격), 기존 작업 대기열, 다운로드 전송은 포함하지 않는다.

최초 작업의 생성기 호출은 100회, 합산 45.61초로 전체의 약 94%였다. 이는 이미지 처리·문서 XML 구성·압축 등을 포함한 생성기 전체 시간이며 이미지 축소만의 시간은 아니다. 로컬 저장소 I/O는 0.145초, JDBC execute 합계는 0.479초였다. 저장소 GET 300회/PUT 105회(문서 100개와 내부 묶음 ZIP 5개), JDBC 800회였다.

재요청은 생성기 호출 0회, 캐시 GET 100회, 새 ZIP PUT 5회, JDBC 600회였다. 기존 문서 캐시가 재사용되는 것은 확인했다. 재요청에도 ZIP과 DB 작업은 다시 발생한다. 실제 R2 왕복은 측정하지 않아 운영에서의 시간 비중은 달라질 수 있다.

사진 없는 결과는 DB/캐시/ZIP 작업을 제외한 별도 실험이다. 원시 데이터의 renderCalls/renderMs는 이 별도 실험에서 계측하지 않아 0이며, p50/p95/mean은 생성기를 감싼 전체 타이머 값이다. 이를 19,000건 전체 다운로드 완료 시간으로 단순 곱하지 않는다.

## 개선 우선순위 제안 — 미적용

1. **목록의 행별 SQL 제거.** 20건 62회 → 100건 302회로 증가했다. 사진 수·검침 상태 등을 일괄 조회하거나 목록 전용 projection으로 통합한 뒤 동일 테스트로 검증한다. 캐시보다 먼저 쿼리 구조를 줄일 근거가 있다.
2. **문서 생성과 반복 요청 비용 감소.** 사진이 있는 문서 생성기 프로파일링, 이미지 처리, 동일 조건 중복 작업 합치기/ZIP 재사용을 검토한다. 병렬화는 메모리 상한을 두고 재측정해야 한다. 사진 없는 운영 데이터에서는 별도의 작업 전체 측정이 필요하다.
3. **검색·지도 실행 계획 개선.** 부분 검색의 pg_trgm 인덱스와 좌표/공간 인덱스를 후보로 검증한다. 현재 2만 건 규모에서 실제 이득과 쓰기 비용을 확인한 뒤 적용한다.
4. **Redis는 반복 집계에 한정해 검토.** 지도 타일/격자 같은 재사용 가능한 키와 무효화 정책이 선행돼야 한다. 사용자별 목록과 사진·검침의 오래된 값을 관리하는 비용까지 고려한다. 현재 측정만으로 필수라고 판단하지 않는다.
5. **SQS 등은 작업 지속성·재시도·웹 요청과의 자원 분리에 목적을 둔다.** 도입 자체가 생성기 연산 속도를 높이지는 않는다. 기존 DB 작업 큐의 지연/복구 문제가 확인될 때 도입 근거가 강해진다.

## 검증 및 남은 범위

실제 실행: `performanceBaseline`의 전체 기준 측정 성공, 사진 없는 생성기 별도 실행 성공. 일반 `test`는 **64개, 실패 0, 오류 0**으로 통과했으며 performance 테스트가 섞이지 않은 것을 XML로 확인했다. 프론트/운영 코드/스키마 변경은 없다.

미측정: 운영 EC2 응답시간과 자원 사용률, 실제 R2 지연, NAVER 지오코딩, Excel 대량 업로드/삭제, 19,000건 전체 생성, 사진 포함/미포함 혼합 분포, HTTP/Cloudflare/브라우저 전체 경로, 장시간 동시 부하. 다음 단계는 운영에 부담이 적은 관측부터 추가하고 이 기준과 비교하는 것이다. 운영 DB/AWS/R2를 변경하지 않았다.
