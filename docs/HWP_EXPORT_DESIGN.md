# HWP 사전 생성 및 ZIP 다운로드 — 다음 작업 설계

- 기록일: 2026-10-23
- 상태: **사용자와 방향 합의 / 구현·성능 검증 전**
- 대상: 10,000건 이상 수용가, EC2 RAM 약 2GB, Spring Boot/Java 21, 비공개 R2
- 템플릿: 사용자 제공 `붙임 2(검침카드 양식).hwp`

## 합의한 흐름

**저장 시 변경된 수용가의 HWP를 백그라운드에서 최신화해 R2에 보관하고, 다운로드 요청 시 대상 HWP를 ZIP으로 묶어 제공한다.**

저장 요청에서 HWP 생성 및 R2 업로드 완료까지 기다리지 않는다. DB 저장 성공과 문서 생성 성공은 별도 상태다. 모든 저장 호출에서 무조건 새 파일을 만드는 것도 아니다. 출력에 영향을 주는 변경만 갱신 대상으로 표시하고, 같은 최신 버전은 재사용한다.

### 입력 저장

1. 기본정보·검침·사진·특이사항 등 출력 데이터 변경을 DB에 저장한다.
2. 같은 트랜잭션에서 출력 데이터 버전을 올리고 문서 갱신 필요 상태를 기록한다.
3. 사용자에게 저장 성공을 응답한다. 문서 생성 실패로 이미 성공한 현장 저장을 되돌리지 않는다.
4. 백그라운드 작업자가 대상을 가져와 기존 HWP의 데이터 버전·템플릿 버전과 비교한다.
5. 최신 파일이 있으면 재사용한다. 없거나 오래됐으면 해당 수용가 한 건만 생성한다.
6. 새 HWP를 비공개 R2에 업로드하고, 성공 후 DB의 생성 버전·파일 키·상태를 갱신한다.

사진 업로드 완료/교체/삭제도 문서 갱신 대상이다. 사진 객체가 실제로 준비된 이후의 확정 메타데이터를 기준으로 한다. 프론트의 저장 요청만으로 업로드 성공을 가정하지 않는다.

### ZIP 다운로드

1. 관리자가 전체 또는 선택 블록 등 출력 범위를 요청한다.
2. 서버가 권한을 확인하고 대상 ID와 사용할 데이터·템플릿 버전을 작업에 기록한다.
3. 누락·오래된 HWP는 먼저 갱신한다. 최신 파일이 없는 항목을 조용히 제외하지 않는다.
4. 준비된 R2 HWP를 한 건씩 읽어 임시 디스크의 ZIP에 순서대로 추가한다.
5. ZIP을 완성한 후 비공개 R2에 업로드한다.
6. 화면에 준비 완료를 표시하고, 권한 확인 후 만료되는 다운로드 링크를 제공한다.

HWP를 미리 만들어도 1만 개 객체 조회·전송·ZIP 기록 시간은 남는다. ZIP도 장시간 HTTP 요청 안에서 생성하기보다 백그라운드 작업으로 처리한다. 프론트는 작업 ID로 진행률/실패/완료를 조회하고 완성 파일을 직접 다운로드한다. ZIP 전체를 브라우저 Blob으로 읽는 방식은 피한다.

## 최신성·실패 처리

- DB와 사진이 원본이며 HWP/ZIP은 재생성 가능한 파생 파일이다.
- 출력 데이터 버전과 생성된 문서의 데이터 버전·템플릿 버전을 관리한다.
- 검침·사진·특이사항의 연속 저장은 마지막 버전으로 묶어 생성하도록 한다. 대기 시간은 구현 시 결정한다.
- 생성 도중 추가 수정이 발생하면, 이전 버전 파일을 최신 완료로 표시하지 않는다. 조건부 갱신으로 확인하고 최신 버전을 다시 처리한다.
- 버전별 불변 R2 키를 사용해 생성 중인 파일이 기존 정상 파일을 덮어쓰지 않도록 하는 방안을 우선 검토한다.
- DB에 대기/생성 중/완료/실패 및 오류·재시도 정보를 보관한다. 프로세스 재시작 후에도 미완료 작업을 복구할 수 있어야 한다. 메모리 이벤트만으로 작업을 관리하지 않는다.
- R2 업로드 성공 후 DB 갱신 실패로 생기는 고아 파일, 중단된 임시 파일과 업로드 정리 정책이 필요하다.
- ZIP 작업은 선택한 HWP 객체 키를 고정한다. 중간 수정 시 어떤 버전을 출력할지, 모든 문서의 단일 시점 일관성이 필요한지는 별도 결정한다. 장시간 DB 트랜잭션을 유지하지 않는다.
- 실패 항목은 사유와 함께 표시한다. 부분 ZIP 허용 여부와 완료 조건은 구현 전에 정한다.
- 템플릿 변경 시 기존 문서를 갱신 대상으로 표시하고 순차 재생성한다.

## 2GB 환경의 자원 제한

- 초기 생성 동시 실행은 서버 전체에서 1개. 여러 요청은 순서대로 처리한다.
- DB는 대상 ID 및 소량 DTO를 나눠 조회한다. 1만 건 JPA 엔티티/사진 바이트를 한꺼번에 유지하지 않는다.
- 한 번에 HWP 한 건만 생성하고 ZIP에 기록한 뒤 임시 HWP와 참조를 해제한다.
- ZIP 전체를 ByteArrayOutputStream/byte[]로 만들지 않는다. ZipOutputStream과 파일 스트림을 사용한다. ZIP 엔트리 메타데이터 등 소규모 메모리는 별도로 발생한다.
- 사진은 한 장씩 처리하며, 픽셀 수를 제한한 출력용 이미지를 우선 사용한다. 원본 4장을 동시에 디코딩하지 않는다.
- JPG/PNG의 압축된 파일 크기와 디코딩 메모리는 다르다. 예: 4,000×3,000×4바이트는 약 48MB이며 중간 복사본은 별도다.
- 임시 ZIP의 디스크 예산·작업 전 여유 공간 확인·만료 정리를 둔다. R2 업로드도 파일 기반/제한된 버퍼를 사용한다.
- JVM 힙 외 메모리와 OS/PostgreSQL도 합산해서 측정한다. 현재는 안전한 Xmx, 최대 파일 크기, 생성 소요 시간을 확정하지 않았다.
- HWP와 ZIP 캐시의 보관 기간은 별도 결정한다. 재요청 시 대상·데이터 버전·템플릿 버전이 같은 완성 ZIP은 재사용 가능하다.

## 템플릿 및 구현 후보

- 기존 양식을 복사해 출력용 템플릿을 만들고 이름 있는 필드/누름틀에 값을 채우는 방식을 우선 검증한다.
- Java hwplib의 HWP 읽기/쓰기·필드 설정·이미지 삽입을 후보로 검토한다. 이 양식의 배치 보존 성공은 아직 검증하지 않았다.
- 위치도 기능은 제외된 상태다. 현재 사진 슬롯은 원경/START 근경/END 근경/임시용의 4종이다.
- 원본 양식의 위치도 칸을 임시용으로 바꿀지, 임시용 사진을 최종 HWP에도 포함할지 확정해야 한다. 사진이 누락된 칸과 긴 주소/특이사항의 출력 규칙도 정한다.
- 현재 HWP 버튼은 준비 상태이며 실제 백엔드 HWP 생성·R2 업로드·ZIP 작업 API는 미구현이다.
- 단일 Spring 애플리케이션과 DB 기반 작업 상태로 시작한다. 별도 메시지 브로커/마이크로서비스는 우선 도입하지 않는다. 세부 스키마·작업 선점·재시도 설계는 개발자가 결정한다.
